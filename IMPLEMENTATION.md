# RestoGuide AI — Implementation Plan

**Project:** RestoGuide AI — a domain-specific RAG assistant for restaurant SOPs, recipes, and customer preferences
**Prepared for:** Patience Njeri Maina
**Source documents:** `proposal.md` (scope & evaluation), `technical.md` (architecture & data flow), `data.json` (knowledge base — 16 Q/A records)

## Decisions locked for this plan

| Decision | Choice |
| --- | --- |
| LLM | `gemini-3.5-flash-lite`, `temperature=0` |
| Embedding model | `gemini-embedding-001` (identical config on both sides of the pipeline) |
| Vector store | ChromaDB, persisted to local disk |
| Chunking | Record-based — 1 JSON record = 1 chunk, never length-split |
| **Embedding strategy** | **Strategy A (default): question-only.** Vector computed from `question` alone; `answer` stored as metadata payload and rendered back into the prompt at query time |
| **Fallback** | **Strategy B: question+answer embedded together**, adopted automatically — no approval needed — if Phase 5 Hit Rate @ k=3 falls below 85 %. Selected by `EMBEDDING_STRATEGY` in `.env`, persisted, followed by a full re-ingest |
| Category metadata | Deterministic keyword rules at ingest time (`classify_category`), default `general` |
| MVP UI scope | **Employee view only.** Manager/RBAC ingestion panel is documented as post-MVP (Phase 6) |
| Multi-turn | **Follow-ups are condensed into a standalone question before retrieval** (Phase 7, built after the MVP closed). History never reaches the embedding or the vector store |
| Re-ingestion | **Full rebuild each run** — wipe the persist directory, re-embed all records |
| Logging | No logging subsystem. Errors are raised/printed at the boundary where they occur (see §4) |

> **Note on model IDs.** `gemini-3.5-flash-lite` and `gemini-embedding-001` are referenced *only* through constants in `src/config.py`. Changing a model is a one-line edit; nothing else in the codebase moves.

### Documented divergence from `proposal.md` and `technical.md`

Both source documents state that each chunk is embedded as `Question: {question}\nAnswer: {answer}`. **This plan supersedes that.** The embedded vector is built from the **question text only**; the answer travels alongside it as metadata payload and is reassembled into the prompt at generation time. Grounding is unchanged — the LLM still sees the full answer verbatim — only what gets vectorised has changed.

*Rationale:* employee queries are themselves questions, so question-to-question comparison puts both sides of the similarity search in the same register, rather than diluting a short question vector with a long procedural answer body.

*Known trade-off:* a query phrased around answer content — "what temperature should cold food be held at?", where `4°C` appears only in the answer — has no matching text in the embedded vector. This is the expected first failure mode.

*Fallback protocol (agreed):* the fallback is **automatic, not escalated**. If Phase 5 reports **Hit Rate @ k=3 below 85 %**, switch to **Strategy B** — question and answer embedded together as `Question: {q}\nAnswer: {a}`, exactly the format `proposal.md` and `technical.md` originally described — by setting `EMBEDDING_STRATEGY=question_answer` in `.env`, re-running ingestion, and re-running the benchmark. No approval is required for this switch; report it after the fact with both benchmark numbers.

A single failed spot-check in Phase 3 does **not** trigger the switch. It is recorded in `eval/spotcheck_failures.md` and folded into the Phase 5 benchmark as an additional test query — a 30-pair benchmark is evidence, one unrepresentative query is not.

Both strategies remain implemented and tested for the life of the project. The A-vs-B comparison is itself a result worth reporting.

`proposal.md` and `technical.md` are deliberately left unedited as submitted deliverables; this section is the authoritative record of the difference.

### Phase 1 — Environment, Shared Config & Schema Validation

**Phase Goal:** A validated `data.json`, a single source of truth for configuration, and a schema module both pipelines agree on — with zero API calls made so far.

**Target files & functions**

| File | Contents |
| --- | --- |
| `src/config.py` | Module-level constants read once via `python-dotenv`: `GOOGLE_API_KEY`, `LLM_MODEL = "gemini-3.5-flash-lite"`, `EMBEDDING_MODEL = "gemini-embedding-001"`, `LLM_TEMPERATURE = 0`, `CHROMA_PERSIST_DIR`, `CHROMA_COLLECTION = "restoguide_kb"`, `DATA_FILE`, `TOP_K = 3`. Plus `EMBEDDING_STRATEGY` (`"question_only"` \| `"question_answer"`, default `"question_only"`, validated against `VALID_STRATEGIES` at import so a typo fails immediately rather than silently indexing under the wrong scheme), `require_api_key() -> str` raising `ConfigError` if the key is absent, and `set_strategy(name: str) -> None` which rewrites the `EMBEDDING_STRATEGY` line in `.env` so an automatic switch survives the process that made it. |
| `src/schema.py` | `REQUIRED_FIELDS = ("question", "answer")`; `VALID_CATEGORIES = {"kitchen", "front_of_house", "safety", "admin", "general"}`; `class RecordError(ValueError)`; `validate_record(raw: dict, index: int) -> dict` (strips whitespace, rejects empty/non-string/missing fields, raises `RecordError` naming the offending index); `make_record_id(index: int) -> str` returning `f"rec-{index:03d}"`. **Two distinct text functions — do not collapse them:** `format_context_text(question, answer) -> str` returns `f"Question: {question}\nAnswer: {answer}"` (what the LLM always reads, under either strategy), and `format_embedding_text(question, answer, strategy) -> str` returns the **question alone** under `question_only` and `format_context_text(...)` under `question_answer`. The strategy is an explicit argument, never read from config inside `schema.py`, so both branches are trivially unit-testable. |
| `data/data.json` | Move the existing `data.json` here unchanged. |
| `tests/test_schema.py` | Asserts `format_embedding_text(..., "question_only")` returns the question alone — no `Question:`/`Answer:` scaffolding, no answer text; asserts `format_embedding_text(..., "question_answer")` equals `format_context_text(...)`; asserts an unknown strategy raises; asserts `format_context_text` round-trips both fields under both strategies; `validate_record` rejects a missing key, an empty string, a non-string value, and a non-dict entry. |

**Data handling rules for `data.json`**

- The file is a JSON **array of objects**, each with exactly `question` and `answer` string keys.
- Both fields are `.strip()`ed. Empty-after-strip is fatal.
- No key other than `question` / `answer` is required; unknown keys are ignored (an explicit `category` key, if a record ever carries one, is honoured over the keyword rules in Phase 2).
- Record ordering in the file defines `record_id` — `rec-000` … `rec-015`. Because ingestion is a full rebuild, IDs are re-derived from file order on every run; reordering the file reassigns IDs, which is acceptable and expected.
- Note the current file has inconsistent indentation on its final record (lines 62–65). That is cosmetically untidy but valid JSON — the validator is what matters, not the whitespace.

**Acceptance criteria**

- `python -c "import json; d=json.load(open('data/data.json', encoding='utf-8')); print(len(d))"` prints `16`.
- Every record validates.
- `src/config.py` resolves `LLM_MODEL == "gemini-3.5-flash-lite"` and `EMBEDDING_MODEL == "gemini-embedding-001"`.

**Verification command**


### Phase 2 — Isolated Data Ingestion & Indexing Pipeline

**Phase Goal:** `python -m src.ingestion.run_ingest` turns `data/data.json` into a persisted ChromaDB collection of exactly 16 embedded chunks. This pipeline is runnable, testable, and deletable without the query side ever noticing — it imports nothing from `src.query`.

**Target files & functions**

| File | Function / class | Responsibility |
| --- | --- | --- |
| `src/ingestion/loader.py` | `load_records(path: str \| None = None) -> list[dict]` | Read JSON, assert top level is a list, run `validate_record` on each, return normalised dicts. Raises `IngestionError` on a malformed file (see §4). |
| `src/ingestion/categorizer.py` | `classify_category(question: str, answer: str) -> str` | Deterministic keyword rules, evaluated in priority order: **safety** (allergy, allergen, hygiene, sanitize, contamination, hand-wash, temperature, spill, caution) → **kitchen** (recipe, prep, cook, boil, sauté, kitchen, equipment, chiller, ingredient, delivery, inventory) → **front_of_house** (guest, server, order, bill, table, greet, complaint, customer, reservation) → **admin** (cash, register, float, M-PESA, POS, shift report, sign-off, opening routine, closing routine) → fallback `"general"`. Case-insensitive, matched over `question + " " + answer`. |
| `src/ingestion/chunker.py` | `record_to_document(record, index, strategy) -> Document` | One record → one `langchain_core.documents.Document`. **`page_content = format_embedding_text(question, answer, strategy)`** — the question alone under Strategy A, the combined pair under Strategy B, because `page_content` is what Chroma vectorises. **Under both strategies the answer is also stored in `metadata["answer"]`**, so the query pipeline reads it from exactly one place regardless of strategy. `metadata = {"record_id", "category", "source", "question", "answer"}` per §3. **Never** invokes a text splitter under either strategy. |
| | `records_to_documents(records: list[dict]) -> list[Document]` | Maps the above over the list; asserts `len(out) == len(records)`. |
| `src/ingestion/embeddings.py` | `get_ingestion_embeddings() -> GoogleGenerativeAIEmbeddings` | Builds the client with `model=config.EMBEDDING_MODEL` (`gemini-embedding-001`) and `google_api_key=config.require_api_key()`. Sole ingestion-side embedding factory. |
| `src/ingestion/indexer.py` | `reset_store(persist_dir: str) -> None` | Full-rebuild semantics: `shutil.rmtree(persist_dir, ignore_errors=True)` then recreate the directory. |
| | `build_index(records, *, strategy=None, dry_run: bool = False) -> IndexReport` | Chunk under the given strategy (defaulting to `config.EMBEDDING_STRATEGY`) → (unless dry-run) embed → `Chroma.from_documents(..., ids=[...], collection_name=..., persist_directory=..., collection_metadata={"embedding_strategy": strategy, "embedding_model": config.EMBEDDING_MODEL})`. Returns a dataclass: `record_count`, `chunk_count`, `collection`, `persist_dir`, `embedding_model`, `strategy`, `dry_run`. |
| `src/ingestion/run_ingest.py` | `main()` under `if __name__ == "__main__"` | `argparse` flags: `--data` (path override), `--dry-run` (validate + chunk + print preview, **zero API calls**), `--limit N` (embed only the first N records, for a cheap smoke test), `--strategy {question_only,question_answer}` (one-off override of the configured strategy, used by the Phase 5 auto-switch and for A/B comparison). Prints the report including the active strategy; exits `1` on failure. |

**Data handling rules**

- **Embedded text depends on `config.EMBEDDING_STRATEGY`:** under `question_only` (default) it is the stripped `question` with no added scaffolding; under `question_answer` it is `Question: {q}\nAnswer: {a}`. Under **both**, the `answer` is stored untouched in `metadata["answer"]`. This is contractual (§3).
- The active strategy is written into the Chroma **collection metadata** at build time, so a store always declares how it was embedded and a mismatch can be detected rather than inferred.
- The answer must survive the round trip byte-for-byte — no truncation, no normalisation of `°C`, quantities, or ratios. Chroma metadata values must be primitives, so store the answer as a plain string.
- Chunk count **equals** record count. `build_index` asserts this and aborts otherwise.
- Chroma IDs are `rec-000` … `rec-015`, matching `metadata["record_id"]`.
- Every run wipes `chroma_db/` first. There is no incremental path in the MVP, so a stale collection can never silently coexist with new data.
- `--dry-run` must be provably API-free — it never constructs the embeddings client at all.

**Acceptance criteria**

- Dry run prints 16 chunks and makes no network call. For each, the preview shows the **embedded text** (the question alone) and the **payload answer** as separate labelled fields, so a reviewer can see at a glance that no answer text is being vectorised.
- A real run persists a collection whose `.count()` is `16`.
- Running ingestion **twice** still yields `16` (proving the rebuild wipes rather than appends).
- `src/ingestion/**` contains zero occurrences of `src.query` / `from ..query`.

**Verification command**

```powershell
python -m src.ingestion.run_ingest --dry-run
python -m src.ingestion.run_ingest
python -m src.ingestion.run_ingest    # second run — idempotency check
python -c "import chromadb; from src import config; c=chromadb.PersistentClient(path=config.CHROMA_PERSIST_DIR).get_collection(config.CHROMA_COLLECTION); print('chunks:', c.count())"
pytest tests/test_ingestion_loader.py tests/test_ingestion_categorizer.py tests/test_ingestion_chunker.py -q
```

Expected: `chunks: 16` after both the first and the second run.

### Phase 3 — Isolated Query & Retrieval Engine

**Phase Goal:** `python -m src.query.run_query "How do I prep the beef wet fry?"` returns a grounded, cited answer from the persisted store — with the ingestion package uninstalled or deleted, it would still work.

**Target files & functions**

| File | Function / class | Responsibility |
| --- | --- | --- |
| `src/query/embeddings.py` | `get_query_embeddings() -> GoogleGenerativeAIEmbeddings` | Same construction as the ingestion factory, reading the **same** `config.EMBEDDING_MODEL` constant. Duplicated deliberately: the two pipelines share the *configuration*, not the *code path*. A drift test (§Phase 5) guards the pairing. |
| `src/query/retriever.py` | `class KnowledgeRetriever` | `__init__(persist_dir=None, collection=None, top_k=None)` opens the **existing** collection — it never creates or writes. Raises `StoreNotFoundError` if the directory or collection is absent, with the message `Vector store not found — run: python -m src.ingestion.run_ingest`. |
| | `.retrieve(query: str) -> list[RetrievedChunk]` | `similarity_search_with_relevance_scores(query, k=top_k)`. **Reassembles each hit into `RetrievedChunk(record_id, category, question, answer, context_text, score)`, where `question`/`answer` come from metadata and `context_text = format_context_text(question, answer)`.** The match was made on the question vector; the answer is retrieved as payload, not matched. Raises `QueryError` if a hit is missing its `answer` key — that means the store was written by an older, incompatible ingestion run. |
| `src/query/prompts.py` | `SYSTEM_PROMPT` | The guardrail: answer **only** from the supplied context; never infer, extrapolate, or supplement with outside knowledge; if the context does not contain the answer, reply exactly `Information not found in the manual.`; for allergy/safety content, quote the procedure without paraphrasing away any step; answer in the user's language (English or Swahili/Sheng) but never translate an ingredient or a temperature into a different value. |
| | `build_prompt(question, chunks) -> str` | Renders numbered context blocks (`[rec-012 | kitchen]` + the chunk's `context_text`, i.e. the reassembled `Question: …\nAnswer: …` pair) followed by the user question. The model always sees the full answer even though only the question was embedded. |
| | `NO_ANSWER_TEXT` | The single canonical refusal string, imported by tests and the UI. |
| `src/query/generator.py` | `get_llm()` / `generate(prompt) -> str` | `ChatGoogleGenerativeAI(model=config.LLM_MODEL, temperature=0)` — i.e. `gemini-3.5-flash-lite`. Returns the response text. |
| `src/query/engine.py` | `answer_question(question: str, *, top_k=None) -> Answer` | The orchestration seam for this pipeline: guard empty/whitespace input → retrieve → **if no chunks clear the relevance floor, return `NO_ANSWER_TEXT` without calling the LLM** → build prompt → generate → return `Answer(text, sources: list[RetrievedChunk], refused: bool, latency_ms: float)`. |
| `src/query/run_query.py` | `main()` | `argparse`: positional question, `--top-k`, `--show-context` (prints retrieved chunks and scores before the answer). |

**Data handling rules**

- The query pipeline **never opens `data.json`.** Its only input is the persisted collection. If it needs a field, that field must be in chunk metadata per §3 — which is precisely why the answer payload is contractual rather than incidental.
- Retrieved `question` and `answer` payloads are inserted into the prompt **verbatim and unmodified** — no summarising, truncating, or reformatting before the LLM sees it. Recipe ratios and temperatures must survive intact.
- `top_k` defaults to `3`, matching the proposal's Hit Rate @ k=3 metric.
- **Spot-check obligation.** Phase 3 verification includes an answer-content query whose keywords appear only in the answer body — e.g. *"what temperature should cold food be kept at?"* (`4°C`, present only in `rec-010`'s answer). This is the known weak point of Strategy A. A failure here does **not** trigger the strategy switch: append the query to `eval/spotcheck_failures.md` and add it to `eval/benchmark.json`, then continue to Phase 4. The switch decision belongs to Phase 5, where 30 pairs of evidence exist.
- Relevance floor: chunks scoring below `MIN_RELEVANCE` (start at `0.35`, tune against the benchmark in Phase 5) are dropped. If that leaves zero chunks, the engine refuses locally — cheaper and more reliable than trusting the model to refuse.

**Acceptance criteria**

- An in-domain query ("What is the ratio of maize to beans for Githeri?") returns the `2 cups maize : 3 cups beans` figure and cites `rec-015`.
- The answer-content spot-check ("what temperature should cold food be kept at?") is run and its result recorded — a miss is logged to `eval/spotcheck_failures.md` and promoted into the benchmark, not treated as a blocker.
- An out-of-domain query ("How do I change a car tire?") returns exactly `NO_ANSWER_TEXT`.
- Running the same query twice returns identical text (`temperature=0` determinism).
- Deleting `chroma_db/` produces the actionable `StoreNotFoundError` message, not a stack trace about a missing file.
- `src/query/**` contains zero occurrences of `src.ingestion`.

**Verification command**

```powershell
python -m src.query.run_query "What is the ratio of maize to beans for Githeri?" --show-context
python -m src.query.run_query "How do I prep the beef wet fry?"
python -m src.query.run_query "What are Mr. Smith's dietary restrictions?"
python -m src.query.run_query "what temperature should cold food be kept at?" --show-context   # answer-content spot-check
```

### Phase 4 — Integration / Interface Layer (Employee View)

**Phase Goal:** A mobile-responsive Streamlit app that an employee can use during a shift. The manager/RBAC panel is **explicitly out of MVP scope** and deferred to Phase 6.

**Target files & functions**

| File | Contents |
| --- | --- |
| `app.py` | Streamlit entrypoint. **Imports `from src.query import answer_question` and nothing from `src.ingestion`** — the UI cannot write to the index by construction. |
| | `@st.cache_resource def get_engine()` — builds the retriever + LLM clients once per session rather than per keystroke. |
| | `render_sidebar()` — dataset info, model names (`gemini-3.5-flash-lite` / `gemini-embedding-001`), and a "vector store not built" banner linking to the ingest command. |
| | `render_quick_actions()` — the proposal's one-click prompt buttons: *Opening Checklist*, *Closing the Kitchen*, *Allergy Procedure*, *Handling a Complaint*, *Beef Wet Fry Recipe*. Each button simply submits a canned question through the same `answer_question` path. |
| | `render_answer(answer)` — answer text, then an expander listing each source's `record_id`, `category`, and score. Refusals render in a neutral info box, never as an error. |
| | `st.set_page_config(layout="centered")` + a small CSS block for tablet/phone width, per the proposal's mobile-responsive requirement. |

**Data handling rules**

- The UI is a pure consumer: it renders `Answer.text` and `Answer.sources` and holds no retrieval or prompt logic of its own. Any temptation to "just tweak the prompt here" belongs in `src/query/prompts.py`.
- Session history is kept in `st.session_state` for the current session only; nothing is persisted to disk (no PII retention, per the proposal's privacy stance).

**Acceptance criteria**

- App boots with no vector store present and shows the build-the-index banner instead of crashing.
- After ingestion, a typed question and each quick-action button both return a grounded answer with visible sources.
- Layout is usable at 390 px width.
- End-to-end response time under 3 s on a warm session (proposal metric).

#### Calibrating the relevance floor (carried over from Phase 3, resolved in Phase 5)

The benchmark showed the two bands genuinely **overlap**, so no flat threshold can separate them:

- Weakest legitimate in-domain top hit: `para-11` at **0.7884**
- Strongest out-of-scope top hit: `neg-06` at **0.7984**

| --- | --- | --- | --- |
| flat 0.80 | 23/24 | 0/6 | 2.46 |

| **relative 0.75 (shipped)** | **24/24** | 5/6 | 1.50 |

`relative 0.75` is the only configuration that answers every legitimate question, and it sends ~40 % less weak context than the flat floor. The trade is that five borderline out-of-scope queries now reach the model, where guardrail 2 refused all of them. Guardrail 1 still blocks the clearly-unrelated case locally in ~550 ms with no generation call.

`tests/test_query_floor.py` locks both modes and the shipped defaults, using the real benchmark scores as fixtures.



`MIN_RELEVANCE` is **0.80**, set in Phase 3 against five real queries. The original `0.35` never fired: `gemini-embedding-001` cosine scores compress into a high band, so guardrail 1 was decorative and every refusal came from the prompt alone.

Observed Phase 3 distribution — note the overlap, which is why no single flat threshold is clean:

| Query | Top | 2nd | 3rd |
| --- | --- | --- | --- |
| Githeri (exact) | 0.989 | 0.829 | 0.720 |
| Mr. Smith allergy | 0.936 | 0.808 | 0.774 |
| Beef wet fry | 0.885 | 0.753 | 0.748 |
| Cold food (answer-body) | 0.835 | 0.831 | 0.829 |
| **Car tire (out-of-domain)** | **0.764** | 0.748 | 0.744 |

**Phase 5 task — evaluate a relative floor.** Once the 30-pair benchmark gives a real distribution, compare the flat 0.80 against a two-parameter relative floor:

1. **Absolute gate on the top hit only** — if the best match fails it, refuse without an LLM call.
2. **Margin below the top hit** — keep other chunks only within that margin of the best score.

The motivation is that a raw score means little alone, but a score relative to the best available match means a lot. On the Phase 3 data with gate `0.80` / margin `0.10`, the Githeri and Mr. Smith queries would retain **only** their single correct record (dropping padding the flat floor keeps), while the diffuse cold-food query would keep all three — a distinction a flat threshold cannot make. Cost: one more parameter to justify, and the risk that too tight a margin starves a question whose answer legitimately spans two records.

Report both configurations' Hit Rate @ k=3 and refusal rate; keep whichever wins, and record the decision here.

#### The automatic Strategy A → B switch

If `run_eval.py` reports **Hit Rate @ k=3 < 85 %** under `question_only`, execute this without asking:

```powershell
python eval/run_eval.py                                            # 1. record Strategy A baseline
python -m src.ingestion.run_ingest --strategy question_answer      # 2. rebuild under Strategy B
python eval/run_eval.py                                            # 3. re-measure
# 4. if B beats A, persist it — config.set_strategy("question_answer") rewrites .env
```

Rules for the switch:

- **All-or-nothing.** The whole collection is rebuilt under one strategy. Never mix — question-only and combined-text vectors occupy different regions of the space, and their similarity scores are not comparable, so a mixed collection ranks incoherently.
- **Keep both result files.** `eval/results.question_only.json` and `eval/results.question_answer.json` are the A/B comparison for the final report — genuinely the most interesting empirical result this project produces.
- **If B is also below 85 %**, the problem is not the embedding strategy. Stop and reconsider `MIN_RELEVANCE`, the benchmark's expected-record labels, or `top_k` before assuming either strategy has failed.
- **If B scores worse than A**, keep A. The trigger licenses a trial of B, not an unconditional adoption of it.
- Report the switch and both numbers when it happens.

### Phase 7 — Conversational follow-ups (built 2026-09-01)

Added after the MVP Definition of Done was closed, in response to a reported failure: asking a follow-up in the app produced a refusal instead of an answer.

**The diagnosis.** The failure was in retrieval, not generation. A bare follow-up has no anchor of its own — `"what about for fish?"` scores **0.7382** against its best match (and that match is `rec-005`, the handwashing station, which acts as an attractor for short contextless questions). It falls below the 0.75 gate, so guardrail 1 refuses locally in ~570 ms without ever calling the LLM. The app already kept the conversation in `st.session_state.history`, but used it only for rendering; `answer_question()` received a bare string.

**Options considered.**

| | Approach | Verdict |
| --- | --- | --- |
| A | Rewrite the follow-up into a standalone question, then run the existing pipeline unchanged | **Chosen** |
| B | Pass history into the answering prompt, retrieve on the raw query | Rejected — does not fix the bug. The floor refuses before the LLM is reached. |
| C | Embed history and query together | Rejected — pollutes the vector with earlier topics, and invalidates a floor calibrated on standalone questions. |

**Why A.** Every threshold in this system assumes a self-contained question: the question alone is what gets embedded under Strategy A, and `MIN_RELEVANCE` was calibrated in Phase 5 against questions that stand on their own. Condensing **restores that precondition** rather than weakening it. B and C either do not work or force the floor to be re-tuned against a moving target.

**What was built.**

- `src/query/condenser.py` — `condense_question(question, history, llm)`.
- `CONDENSE_SYSTEM_PROMPT` and `build_condense_prompt()` in `src/query/prompts.py`, which continues to own all prompt wording.
- `generate()` gained a `system=` keyword so the condenser can share its retry and empty-response handling without inheriting the answering rules.
- `answer_question(..., history=None)` and a new `Answer.searched_for` field.
- `eval/benchmark_multiturn.json` (15 cases) and `eval/run_eval_multiturn.py`.

**Decisions worth preserving.**

1. **Condensation happens before retrieval**, so §3 is untouched, no re-ingest is needed, and the floor was not re-tuned. The change is confined to `src/query/`; pipeline isolation is unaffected.
2. **No history means no API call.** Single-turn queries return the question unchanged, so the 30-pair benchmark and its latency are unaffected.
3. **The condenser uses its own system prompt.** The answering rules and the rewriting rules contradict each other — one forbids going beyond the context, the other must reword freely. Mixing them is the same class of prompt-rule conflict that caused the false refusals fixed in `017a1a1`.
4. **A malformed rewrite falls back to the raw question.** Multi-line output, anything over `MAX_CONDENSED_CHARS`, or an API failure degrades to the previous stateless behaviour — a known-safe outcome. Raising would turn a follow-up into an error for an employee mid-shift.
5. **Rule 6 forbids steering an off-topic question towards a nearby one.** This is load-bearing rather than stylistic: `negfollow-03` ("what about chicken biryani?" after a recipe question) condenses into a well-formed recipe question aimed straight at `rec-012`, and both guardrails must hold on it.
6. **`Answer.searched_for` is surfaced in the UI** as "Understood as: …". An employee who gets a surprising answer must be able to see what was actually searched.

**Results** — `eval/benchmark_multiturn.json`, 10 follow-ups and 5 out-of-scope follow-ups, both artifacts committed:

| Metric | Stateless baseline | Condensed |
| --- | --- | --- |
| Follow-ups resolved | 2/10 | **10/10** |
| Out-of-scope follow-ups refused | 5/5 | **5/5** |

The ground truth was written and baselined **before** the condenser existed, so the target was measured rather than assumed. `follow-09` and `follow-10` pass in both columns by design — they are already self-contained, and serve as controls against a condenser that merges history when it should not.

Single-turn regression check after the change: Hit Rate @ k=3 100 %, refusal rate 100 %, unchanged.

**Cost and open items.**

- A second LLM call on every follow-up turn: mean ~7 s against ~2.3 s single-turn. Two untaken mitigations: skip condensation when the question already parses as standalone, or run the condenser on a faster model than the answering one.
- `run_eval_multiturn.py` exits non-zero on a **leaked** out-of-scope answer but not on an unresolved follow-up. An unresolved follow-up is a missed convenience; a leak is a fabricated procedure.
- Conversation memory is per-browser-session (`st.session_state`) and resets on reload. Nothing is persisted, and no history reaches the vector store.
- The query path still has no retry of its own, unlike ingestion — a transient 504 from the embedding API surfaces to the employee as an error. `run_eval_multiturn.py` carries its own retry to work around this; the pipeline does not.

## 3. Pipeline Interface Contract

This is the **only** coupling between `src/ingestion/` and `src/query/`. Neither package imports the other; both are written against this document. Any change here is a breaking change requiring a re-ingest and an update to `tests/test_contract.py`.

### 3.1 Handoff medium

A ChromaDB **persistent collection** on local disk. The ingestion pipeline is the sole writer; the query pipeline is a strict reader.

| Property | Value | Source |
| --- | --- | --- |
| Persist directory | `./chroma_db` | `config.CHROMA_PERSIST_DIR` |
| Collection name | `restoguide_kb` | `config.CHROMA_COLLECTION` |
| Embedding model | `gemini-embedding-001` | `config.EMBEDDING_MODEL` |
| Distance metric | cosine (Chroma default) | — |
| Item count | exactly `len(records)` — 16 today | invariant |
| Embedding strategy | `question_only` (default) or `question_answer` | `config.EMBEDDING_STRATEGY`, recorded in collection metadata |

### 3.2 Per-item shape

**Embedding strategy is a contract variable with two permitted values.** `document` (Chroma's `page_content`) is whatever was embedded — the question alone under `question_only`, the combined pair under `question_answer`. **Regardless of strategy, `metadata["question"]` and `metadata["answer"]` are both always present**, which is what lets the query pipeline stay strategy-agnostic: it always reads the two fields from metadata and never parses `page_content`. Switching strategies therefore changes retrieval quality and nothing else — no query-side code changes.

The example below shows `question_only`, the default.

```python
{
  "id":        "rec-007",                         # f"rec-{index:03d}", index = position in data.json
  "document":  "What steps must be followed when a customer informs staff "
               "of a severe food allergy?",       # QUESTION ONLY — this is what gets embedded
  "embedding": [...],                             # gemini-embedding-001, computed from `document`
  "metadata": {
      "record_id": "rec-007",                     # str — mirrors id, used for citation in the UI
      "category":  "safety",                      # str — one of VALID_CATEGORIES
      "source":    "data.json",                   # str — provenance
      "question":  "What steps must be followed when a customer informs staff of a severe food allergy?",
      "answer":    "Inform the kitchen manager immediately, clean and sanitize all food prep "
                   "surfaces and utensils before preparing the order, ...",   # PAYLOAD — not embedded
  },
}
```

At query time the retriever recomposes `format_context_text(question, answer)` → `"Question: …\nAnswer: …"` for the prompt. That string exists only in memory; it is never stored and never embedded.

### 3.3 Guarantees the ingestion pipeline makes

1. `page_content` is exactly `format_embedding_text(question, answer, strategy)` for the strategy named in the collection metadata — the stripped `question` under `question_only`, or `Question: {q}\nAnswer: {a}` under `question_answer`. No truncation, no length-based splitting, under either.
2. Chunk count equals record count; one record never yields two vectors, and two records never merge.
3. Every item carries all five metadata keys, all string-typed and non-empty — `answer` included. An item without a usable `answer` payload is unanswerable at query time and must fail the build, not ship.
4. `category` is drawn from `schema.VALID_CATEGORIES`.
5. The collection is written with `gemini-embedding-001` and no other model, under exactly one strategy, declared in `collection_metadata["embedding_strategy"]`.
6. Every run leaves the collection in a complete state or fails loudly — a full rebuild either replaces the whole collection or aborts before wiping (build to a temp dir, swap on success).

### 3.4 Expectations the query pipeline is allowed to hold

1. The collection exists at the configured path and name, or `StoreNotFoundError` is raised with the ingest command in the message.
2. It may embed a query with `gemini-embedding-001` and compare it directly against stored vectors — **same model, same configuration, same vector space.** This is the single most important line of the contract: a mismatch produces confident, plausible, wrong answers with no error to warn you.
3. `metadata["record_id"]` and `metadata["category"]` are always present and safe to render as citations.
4. `metadata["answer"]` is always present and holds the complete, unmodified answer, **under both strategies**. **The query pipeline must read question and answer from metadata — never by parsing `page_content`, whose shape depends on the strategy.** This is what keeps the query pipeline strategy-agnostic.
5. `metadata["question"]` and `metadata["answer"]` are safe to inject verbatim into the LLM prompt via `format_context_text`.
6. Under `question_only`, similarity scores reflect question-to-question proximity only: a low score means *"no stored question resembles this query"*, **not** *"the knowledge base lacks this"*, since answer-body content is invisible to the search. Under `question_answer` the scores lose that guarantee but gain answer-body reachability. `MIN_RELEVANCE` is strategy-dependent and must be re-tuned after a switch — a threshold calibrated on A is not valid for B.
5. The store is read-only from the query side. The query pipeline never calls `add`, `update`, `delete`, or `from_documents`.

### 3.5 Contract drift guard

`tests/test_contract.py` re-verifies §3.2–§3.3 against the live persisted store after every ingest, and a dedicated assertion checks `src.ingestion.embeddings` and `src.query.embeddings` both resolve to `config.EMBEDDING_MODEL` — so the two factories can never drift apart while staying independently implemented.

## 4. Edge Cases & Error Handling

No logging subsystem is used. Each pipeline defines its own exception type and fails at its boundary with a message that names the fix; the CLIs print that message and exit non-zero, and the Streamlit layer renders it as user-facing text.

Exception types: `src/schema.py → RecordError`; `src/config.py → ConfigError`; `src/ingestion/ → IngestionError`; `src/query/ → QueryError`, `StoreNotFoundError`.

### 4.1 Ingestion failures

| Case | Detection | Handling |
| --- | --- | --- |
| `data.json` missing / unreadable | `FileNotFoundError` in `load_records` | Raise `IngestionError("data file not found at {path}")`; exit 1. Never create an empty file. |
| Malformed JSON (trailing comma, bad brace) | `json.JSONDecodeError` | Re-raise as `IngestionError` including `e.lineno`/`e.colno` so the bad line is pinpointed. Nothing is written to Chroma. |
| Top level is not a list | Type check in `load_records` | `IngestionError("expected a JSON array of records, got {type}")`. |
| Record missing `question` or `answer` | `validate_record` | `RecordError` naming the record index. **Fail the whole run** — a partially indexed knowledge base is worse than no index, because retrieval silently returns the wrong neighbour. |
| Empty / whitespace-only field | `validate_record` after `.strip()` | Same as above. |
| Duplicate questions | Post-load set check | Warn to stdout with both indices and continue — duplicates are wasteful but not corrupting. |
| Embedding API timeout / 5xx | Exception from the embeddings client | Retry with exponential backoff (3 attempts: 2 s, 4 s, 8 s). On final failure, abort **without** touching the existing collection — build into a temp directory and swap only on success, so a failed run leaves yesterday's working index intact. |
| Rate limit (429) | HTTP status | Same backoff path, longer base delay; batch embeddings (`batch_size=16`) so 16 records is a single request. Suggest `--limit` for cheap iteration. |
| Missing `GOOGLE_API_KEY` | `config.require_api_key()` | `ConfigError("GOOGLE_API_KEY not set — copy .env.example to .env and add your key")`. Raised before any chunking work. |
| Chunk/record count mismatch | Assertion in `build_index` | Abort. Signals a chunker regression — the record-based-chunking invariant is broken. |
| Embedded text disagrees with the active strategy | Assertion in `build_index`: `doc.page_content == format_embedding_text(q, a, strategy)` | Abort with `IngestionError("embedded text does not match strategy '{strategy}'")`. Guards whichever strategy is active at write time, not just in tests. |
| Unknown `EMBEDDING_STRATEGY` value in `.env` | Validation at `config` import | `ConfigError` listing the two valid values. A typo must never fall back to a default silently — that would index under one scheme while the report claims another. |
| Strategy changed without re-ingesting | `build_index` compares requested strategy against existing `collection_metadata` | Full rebuild is mandatory on a strategy change; since every run rebuilds anyway this is automatic, but the check makes the requirement explicit rather than incidental. |
| Answer missing from payload | Assertion in `build_index` | Abort. A vector with no answer payload is retrievable but unanswerable — worse than absent. |
| Locked `chroma_db/` on Windows (app running) | `PermissionError` during `rmtree` | `IngestionError("close the Streamlit app before rebuilding the index")`. |
| Staging directory cannot be swapped into place | `PermissionError` during `rename` — **hit for real in Phase 2** | Chroma caches its client system-wide, so discarding the vector store object does not close the sqlite handle. Call `SharedSystemClient.clear_system_cache()` plus `gc.collect()` after the write, then retry the rename with a short backoff. Without this, every ingest run fails at the swap on Windows. |

### 4.2 Query failures

| Case | Detection | Handling |
| --- | --- | --- |
| Vector store absent / never built | `KeyError` or missing dir in `KnowledgeRetriever.__init__` | `StoreNotFoundError("Vector store not found — run: python -m src.ingestion.run_ingest")`. UI shows this as a banner with the command. |
| Empty / whitespace query | Guard in `answer_question` | Return a prompt-the-user message. No API call, no retrieval. |
| Out-of-domain question ("how do I change a car tire?") | All chunks below `MIN_RELEVANCE` | Return `NO_ANSWER_TEXT` **locally, without calling the LLM.** Two independent guardrails — the relevance floor and the system prompt — so a single failure does not become a fabricated answer. |
| Query targets answer-body content, not a stored question | Manual spot-check + Phase 5 benchmark | The structural blind spot of Strategy A: "what temperature for cold food?" has no matching text in any embedded vector. Log spot-check misses; if Phase 5 Hit Rate @ k=3 falls below 85 %, **switch to Strategy B automatically** per the Phase 5 procedure. If B also underperforms, the remaining levers are LLM-generated paraphrase questions per record or hybrid keyword+vector search — raise those with the user rather than adding a third strategy unprompted. |
| Retrieved hit missing its `answer` payload | Check in `KnowledgeRetriever.retrieve` | `QueryError("vector store is stale or was built by an incompatible ingestion run — re-run: python -m src.ingestion.run_ingest")`. Never send an answerless chunk to the LLM; it invites the model to fill the gap from its own knowledge. |
| Retrieval returns chunks, but none actually answers | System prompt instruction | The model must emit `Information not found in the manual.` The prompt forbids partial-credit answering. Every generated answer is displayed with its sources so a user can see the basis for it. |
| Hallucination risk on safety content | Prompt constraint + citation UI | Allergy, temperature, and ratio content must be quoted from context, not paraphrased. Sources are always displayed alongside the answer, never hidden behind a toggle by default for safety-category chunks. |
| LLM API timeout / 5xx | Exception in `generator.generate` | One retry, then `QueryError("the assistant is unreachable right now — check your connection and try again")`. Never fall back to answering from the model's own knowledge. |
| Rate limit (429) | HTTP status | Surface a plain "too many requests, wait a moment" message; do not silently degrade to an ungrounded answer. |
| Model returns empty text | Post-call check | Treat as a failed generation and surface `NO_ANSWER_TEXT` rather than a blank panel. |
| Prompt-injection text inside a query | System prompt precedence | The system prompt states that retrieved context and user input are data, never instructions, and that its own rules cannot be overridden by anything in the user message. |
| Non-English (Swahili / Sheng) query | Prompt instruction | Answer in the user's language, but never translate a quantity, temperature, or ingredient into a different value. If retrieval fails on a Swahili phrasing, that is a benchmark finding for Phase 5, not a runtime error. |
